# 横屏收起的帧耗时与首页输入修复

- 日期：2026-10-23
- 基线：`main ***`，`versionCode=6 / 0.1.0-dev.rotation5`
- 修复构建：`versionCode=8 / 0.1.0-dev.rotation7`
- 设备：Xiaomi 23049RAD8C / Android 15（API 35），USB ADB
- 范围：常规播放器展示与 Activity；未修改功耗实验代码线

## 问题与修复

旧实现把“展示会话尚未结束”同时用于整屏输入阻断。首页已经显露时，仍要等待收起弹簧精确到零、隐藏旋转角归零及系统方向/尺寸回执；透明遮罩也继续消耗触摸。现在关闭意图成立且进度不大于 0.5 时，即放开首页滚动、点击及返回键。系统交接仍使用原有生命周期及方向锁存，视频命中区域随画面继续缩放旋转。

系统方向交接时，安全区包装器曾随画布方向重建，静态 CompositionLocal 因此失效整棵首页；隐藏的全屏控件也继续执行响应式布局测量。现在安全区提供器保持身份稳定，在 Insets getter 中读取最新画布、角度、持有状态；隐藏控件保留组合与交互状态，仅停止其子树测量，重新显示时按当前约束测量。

收起期间根组合直接读取连续进度，展示 Layout 捕获每帧几何参数，端点副作用也逐帧重启。现在用离散阶段驱动组合，在固定尺寸的图层回调中更新连续变换，并取消首页与黑色遮罩叠加的双重整页透明度合成。视频 View、SurfaceTexture 及生产者尺寸保持原有所有权。

视频 window bounds 以前每帧触发 PiP 参数重建与系统发布。现在逐帧只记录本地最新矩形，在完整展开对齐或显式 PiP 进入时发布；设备能力、RemoteAction、PendingIntent 缓存复用。

## 基线取证

安装新包之前，在原有本地横屏视频暂停于约 0:32 的状态下，保持液态玻璃底栏及原有目录列表，独立采集三次“打开迷你条 → 等待 1.5 秒 → reset gfxinfo → Back → 等待 1.8 秒”的窗口。

| 样本 | UI 帧数 | Janky frames | p95 | p99 |
| --- | ---: | ---: | ---: | ---: |
| 0 | 95 | 7 | 30 ms | 97 ms |
| 1 | 93 | 6 | 44 ms | 77 ms |
| 2 | 92 | 8 | 42 ms | 97 ms |

单独一轮 atrace 的主线程 Back 到 statusBars Insets 动画结束为 1.061 秒。95 次普通 doFrame 中有 5 帧超过 16.667 ms、2 帧超过 33.333 ms；连续两帧分别约 36.440 / 42.310 ms。该窗口有 90 次 `Recomposer:recompose`、85 次 `AndroidOwner:measureAndLayout`。最慢帧内重组切片达 30.697 ms；这些是可能嵌套的墙钟耗时，不能相加当作 CPU 时间。

这份 atrace 与三个 gfxinfo 样本分别采集。Binder 事件只有事务编号，不能直接把其耗时或数量归因 PiP。未从这些记录确认系统窗口冻结。gfxinfo 描述应用 UI 帧，不代表解码视频 FPS；不使用启动以来的累计 jank 数字计算修复收益。

## 修复后同场景采样

最初 rotation6 已减少动画早期的组合与布局耗时，但三轮 gfxinfo 合计 276 帧中仍有 22 个 janky frame（7.97%），系统换轴附近还有 3 个超过 33.333 ms 的主线程帧。因此没有据此宣布卡顿修复，继续处理安全区提供器与隐藏控件测量。

最终 rotation7 恢复同一暂停位置、列表和底栏，按上述流程重新采集：

| 样本 | UI 帧数 | Janky frames | p95 | p99 |
| --- | ---: | ---: | ---: | ---: |
| 0 | 90 | 5 | 25 ms | 48 ms |
| 1 | 89 | 6 | 30 ms | 57 ms |
| 2 | 89 | 6 | 29 ms | 57 ms |

基线合计 280 帧 / 21 个 janky frame（7.50%），最终样本为 268 帧 / 17 个（6.34%）；每次采样 p95 从 30–44 ms 降到 25–30 ms，p99 从 77–97 ms 降到 48–57 ms。仅使用各 dumpsys 文件的第一份汇总，避免重复计算后续窗口统计；未解释 OEM 的 PROFILEDATA Flags=32，未据此推断逐帧连续性。这是单台设备、Debug 构建、暂停视频的三次观察，仍有长帧，不是所有设备零卡顿或视频解码帧率的证明。

另一次最终 atrace 的同口径动作窗口为 1.035 秒，95 次完整普通 doFrame 中仅 1 帧超过 16.667 ms，但该帧达到 56.198 ms，比基线单次 trace 的最大值更高。因此只能确认布局工作与常见帧耗时下降，不能声称最坏帧已经消除。`Recomposer:recompose` 总跨度从 299.586 ms 降到 229.022 ms，`AndroidOwner:measureAndLayout` 从 85 次 / 181.421 ms 降到 56 次 / 51.352 ms；在 Back 后 0.5–0.8 秒的系统交接窗口，measure/layout 从 24.718 ms 降到 5.105 ms。这些跨度不当作 CPU 时间或视频帧率。

## 回归设计

- `PlayerHomeInteractionTest`：实际 `ZivPlayerApp` 与 80 项队列，Compose 时钟收起推进 160 ms，验证触摸滚动与返回键已生效；同时断言尚未发送返回系统方向请求。该时间是受控测试时钟，非所有设备的输入延迟承诺。
- `PlayerPresentationContinuityTest`：连续改变展示进度，验证承载组合与测量计数不变、TextureView 仍为同一个实例。
- 新增隐藏控件用例从首次未显示开始，覆盖显示、隐藏后窗口换轴/尺寸变化及再次显示，检查测量计数、最新约束和未销毁的组合状态。Insets 用例同时检查提供器身份不变与 getter 消费者重新测量，防止“对象稳定但布局不更新”。
- 现有旋转交接、双底栏锚点与真实合成视频用例继续覆盖中断、方向回执、迷你/全屏/PiP、Surface 连续性和实时出帧。低频采样只能证明仍有新画面，不能证明每帧无掉帧。

## 真机回归与恢复

- 最终 rotation7 的 23 项 instrumentation 用例全部通过（89.848 秒），包含首页滚动/返回、图层更新不重组/测量、隐藏控件与安全区新增用例、旋转交接、两种底栏以及 `ContinuousPlaybackDeviceTest`。
- 中间 rotation6 的 21 项曾通过，但后续新增隐藏控件计数测试发现外层 modifier 的门控不能阻止内部布局独立测量；早期 rotation7 的 23 项中有 1 项失败，没有作为通过结果。把门控移到旋转 Layout 自身的测量策略后，先通过 7 项定向用例，再执行上述最终 23 项。一次中途锁屏的旧执行出现 `No compose hierarchies`，已中止；用户解锁后重新执行。
- 实际合成视频在迷你、展开、横屏收起后、手动 PiP、自动 PiP 五个阶段各取得 5 个不同 Surface 时间戳和 5 个不同像素哈希。展示切换保持同一个 TextureView/SurfaceTexture；播放事件仅在主动进行暂停预览测试时变为暂停，交接期间没有额外暂停事件。
- 使用原有本地视频和目录列表，Back 命令派发后约 0.299 秒发起 120 ms 滑动，约 0.518 秒返回。手势按当时横屏窗口坐标输入，收起后的列表已滚到后续条目；不需要再补一次竖屏滑动。ADB 命令返回时间包含传输开销，不等同于逐帧输入延迟。
- 测试前立即备份 DataStore 与 Room 数据库（含 WAL/SHM），测试后恢复并逐文件核对 4 个 SHA-256 全部一致，再正常启动应用。未清空应用数据或恢复旧 APK。
- 媒体音量恢复为测试前 `0/150`；自动亮度、亮度值、方向锁、三个动画比例核对与测试前一致。息屏等待原值为 `600000 ms`，最终复测临时设为 `1800000 ms`，结束后恢复为 `600000 ms`。测试夹具进程已停止。

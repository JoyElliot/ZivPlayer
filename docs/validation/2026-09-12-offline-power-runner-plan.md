# 手机端独立功耗测试控制方案

状态：代码路径已核验，手机已于 08:41 重新连接并在 08:55 完成恢复。只读探测已确认设备提供 `setsid` 和 Toybox `nohup`；独立控制程序尚未实现，断连存活和完整播放验证尚未执行。当前已完成的数据和冻结采集文件保持原样。

## 问题与边界

9 月 12 日 03:20 的 Windows WLAN 断联持续约 131 秒，导致第 18 轮无线 ADB 失联；电脑恢复网络后，旧手机调试入口仍不可用。当前控制器每轮依赖电脑发起下一次 instrumentation，恢复设置也依赖 ADB，因此无法在这种故障下独立完成整夜任务。详见[本次证据和数据](2026-09-12-playback-power-comparison.md)。

保持现有正式 APK 和测试 APK可行，但不能把全部轮次放进同一应用进程。`PlaybackExperiment.configureForInstrumentation` 的配置只在当前进程有效，每轮仍须先停止目标应用、确认旧进程消失，再启动一次新的 `am instrument`。

## 最小实现方向

由电脑生成固定的逐轮清单，发送到本次专属 `/data/local/tmp` 目录；手机上独立的 shell UID 控制程序按清单执行。ADB 用于启动前部署与最终取回文件，计量过程与两轮之间的控制不再依赖电脑在线。

每轮沿用现有测试入口和参数：90 秒预热、240 秒计量、相同 Surface、片源、引擎及解码模式。测试继续将 JSON/JSONL 保存在应用的持久结果目录。shell 控制程序另存实际开始/结束时间、退出状态、起始电池与屏幕信息、顺序及序号；取回时与原始报告合并，不能猜测或补造这些字段。

需要从 `tools/run-power-benchmark.py` 移植的行为：

- `screen_state`、`refresh_idle_screen`、`parse_user_activity`：核验 Awake、解锁及 HOME 后真实活动时间递增，计量内不发 HOME。
- `battery` 与冷却循环：物理放电、起温 ≤36°C、最少冷却 90 秒、最多 1200 秒；冷却结束、开始播放前再次确认电量 ≥28%。现有脚本只在冷却前检查这一电量下限，最终审计虽会拒绝低于下限的轮次，新的控制程序仍应主动阻止启动。
- 逐轮独立应用进程、持久结果防覆盖，以及完整 instrumentation 参数。
- 相互独立的命令看门狗与结果完成宽限。正常协议尾部的 `INSTRUMENTATION_CODE: -1` 不是 shell 退出码；二者分别记录。
- 屏幕临时超时 900000 ms，结束时恢复启动前保存的值（本次为 600000 ms）；同时保存、恢复实际改动的蓝牙等用户设置，并逐项核验。

设备端不能只凭 `am instrument` 的退出码判断合格。必须等待测试最终写入清理结果；完整的 241 点计量、时间跨度和间隙、积分及块顺序门槛，仍需由现有原始数据审计核验。

## 先做的实机验证

手机设置恢复、第 18 轮隔离归档、退出记录读取及个人数据核对均已完成。08:48 的只读探测确认 `/system/bin/setsid` 存在，Toybox 0.8.11-android 提供 `setsid [-cdw]` 与 `nohup COMMAND...`。当前 shell 的 `nohup` 有别名，后续验证宜使用显式 `/system/bin/toybox nohup`；其帮助命令退出码为 125，但已输出该命令的用法，不能将此解读为命令不存在。证据见 `native/out/power-comparison-20260912/recovery-20260912-0841/shell-capabilities.json`。

本次未启动后台心跳、主动断网或播放验证，以保留手机白天使用窗口。上述命令可用不等于已经证明进程能脱离 ADB 持续运行。

随后在用户可恢复连接的时间窗内，验证以下项目：

1. 实际检查 `setsid`、`nohup`、`run-as`、`pidof` 及所需 shell 命令的支持情况；标准输入、输出和错误均重定向，记录 PID、会话和进程组。
2. 独立心跳进程脱离 ADB 后持续运行。`nohup` 或 `setsid` 命令存在，不等于已经证明能躲过 adbd 的子进程清理。
3. 用独立验证标签执行一个完整 90+240 秒播放轮次，主动断开连接，再取回完整 JSON/JSONL，确认应用收尾。仅断开电脑客户端不能代替手机网络丢失场景，两者需分别验证；故障演练数据不计入功耗比较。
4. 演练取消、命令超时、原始结果缺失及清理失败。取消标记必须在等待 instrumentation 时仍可被处理，并停止本轮目标应用；恢复超时和屏幕状态的结果持久记录。

trap 无法保证在 SIGKILL 或重启后执行。需要持久记录正在运行的轮次，并保留恢复连接后的独立收尾入口。不得以“控制程序退出”代替“设备已恢复”的核验。

## 无线网络仍是测量变量

手机端独立运行只解决控制连接依赖，不自动消除 Wi-Fi 自身断联、重连造成的功率变化。继续采用本次无线开启条件时，必须具备设备侧网络状态变化的可核验记录；若无法可靠记录，应改用计量期间 Wi-Fi 关闭的新协议，结束后再恢复网络。

如果改变无线状态、采样代码或其他计量条件，必须建立新 cohort，不能把新数据与当前 17 轮直接混合。具体取舍在实机探测后冻结，不能为了拼齐现有数字而隐去条件变化。

# ADR 0015：各平台原生开发与共享行为契约

- 状态：已接受
- 日期：2026-09-09
- 补充与调整：[ADR 0001](0001-android-kotlin-and-miuix.md)、[ADR 0005](0005-pure-player-contract-and-serialized-runtime.md) 中的跨平台方向

## 背景

ZivPlayer 的长期目标是支持多个平台，当前先交付 Android 版本。各平台客户端采用该平台的原生语言和工具链，重视播放性能、系统集成与原生交互体验。

现有 `core` 模块隔离了 Android、Compose、Media3 和 JNI 依赖，但产物仍是 Kotlin/JVM 库，接口使用 Kotlin 协程和 `Flow`。这种模块隔离有助于维护与测试，不代表 Swift、C++ 等客户端已经能够直接使用同一份核心产物。

早期文档预留了迁移 Kotlin Multiplatform 的方向。本次将其明确为可选技术方案，后续平台不会因为这一预留而被要求采用 Kotlin 实现应用层。

## 决定

### 平台实现

- Android 继续使用 Kotlin、Jetpack Compose 和 MIUIX，保留现有模块边界。
- 后续平台分别选择原生语言、UI 框架和构建工具。例如，Apple 平台可使用 Swift 及其原生 UI 框架；具体平台与实施顺序另行确定。
- 文件权限、媒体会话、音频焦点、后台生命周期、窗口和视频输出等能力留在平台适配层。
- 不要求共享整套 UI、Android 服务、数据库实现或 Kotlin 运行时，也不因跨平台计划立即改写现有 Android 核心。

### 共享边界

| 内容 | 处理方式 |
| --- | --- |
| 播放队列、状态迁移、跳转、错误和恢复语义 | 用语言无关的文档及测试场景统一行为 |
| 设置与可交换数据 | 在存在跨端交换需求时定义有版本的数据格式；各平台存储实现可以不同 |
| libmpv、FFmpeg 等底层原生代码 | 根据目标平台评估源码复用，分别编译、适配和验证 |
| 自研业务逻辑或算法 | 根据维护成本、性能与接口稳定性决定分别实现或提取公共库 |

公共行为契约需要明确：切换媒体后如何丢弃旧回调；连续跳转如何合并及识别完成；`Stop` 与 `ClearQueue` 的区别；关闭和错误恢复的边界。这些规则可参考当前 Android 实现，但跨端规格不直接采用 `StateFlow`、JNI 类型或 Android 文件 URI 作为通用接口。

若需要共享二进制实现，须另行定义跨语言接口、生命周期、错误和线程约束。当前不预设 C ABI、代码生成或 Kotlin Multiplatform 中的某一种方案。跨端测试场景和公共产物接口属于后续实施工作，本决策不表示它们已经实现。

### 性能原则

各平台可以使用共同的 C/C++ 原生库，同时保持客户端原生开发。性能通过目标设备上的解码、渲染、拷贝、调度和功耗测量判断；选定语言本身不构成性能验收。视频帧等高吞吐数据应尽量留在原生处理链路中，避免为通用接口引入不必要的复制或高频跨语言往返。

### 仓库与分支

- 当前保留单仓库和 `main`，模块、目录分别承担组件和平台边界。
- 后续原生客户端可以在同仓库使用各自的构建系统，无需按平台建立长期分支。
- 出现独立使用者、稳定公共 API、独立维护团队或发布节奏时，再评估拆分仓库。
- 开发分支暂不引入；上线后再确定 beta 与稳定版的版本管理方式。

## 影响

现有 Android 代码可以继续演进。各端独立实现会增加一部分重复代码，因此需要通过共同的行为规范和测试场景避免功能差异。共享底层源码也需要逐平台处理编译、系统集成和性能验证，不能直接复用 Android 的 `.so` 或 JNI 层。

当前最重要的准备是维持清晰的平台边界，并在新增跨端需求时固化行为契约。第二个平台启动时，再依据具体需求选择代码复用范围和技术方案。
